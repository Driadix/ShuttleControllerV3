# V1 execution timing and resource evidence

## Research snapshot

This asset answers GitHub issue 11 using only production code and production configuration from [`Driadix/ShuttleController@708d090980155d4a8d4644f7bcf87c383e81cd1d`](https://github.com/Driadix/ShuttleController/tree/708d090980155d4a8d4644f7bcf87c383e81cd1d), the `main` tip verified on 2026-08-02.
The local mirror was clean and its `HEAD` and fetched `origin/main` both resolved to that SHA.
No refactor branch, `docs/Controller-Nonblocking-Refactoring-Plan.md`, refactor artifact, secondary description, or test-only value is used as evidence.
V1 is descriptive evidence, not a V3 requirement or budget.

The gate names used below are those requested by the ticket: safety reaction, watchdog feeding, CAN/UART RX/TX, sensor acquisition/freshness, link health, operation step, and CPU/RAM/stack/queue.

## Classification and bounds

- `measured` means an observed value captured from the production target under a stated workload and measurement method.
- `configured` means a literal, persisted setting, compile-time capacity, or selected production profile found in source.
- `inferred` means an analytical consequence of control flow or configured values, not a target measurement.
- `unknown` means production source does not establish the value or bound.
- A configured timeout is not automatically an execution-time upper bound because its check can be delayed by blocking work.
- A finite loop counter is not automatically a wall-clock upper bound when its body calls an unbounded peripheral API or drain.
- An analytical estimate or source-level bound is never called a measured worst case in this asset.

## Main findings

1. No target timing, WCET, loop-jitter, CPU-load, RAM high-water, stack high-water, or queue high-water measurement is committed at the production SHA.
2. V1 is a single cooperative foreground whose long operations call `SystemYield()`, but `SystemYield()` itself performs safety, watchdog, radio configuration, BMS, telemetry, and complete display/radio RX drains.
3. Bumper IRQs only latch an event; applying a zero motor command waits for the next foreground `handlePendingCrash()` call, whose dispatch latency has no source-provable upper bound.
4. ToF and AS5600 freshness thresholds exist, but acquisition and stale recognition share the foreground and blocking Wire calls for which production code configures no timeout.
5. UART, BMS, and CAN drains have no per-call byte/frame budget, so continuously replenished input can make one cooperative service invocation unbounded.
6. Several local bounds are useful inputs: 128-byte protocol parser buffers, a 64-byte BMS RX frame, two named 256-entry CAN queue selections, fixed telemetry eligibility periods, finite radio AUX/config timeouts, and finite sensor-health windows.
7. Those local bounds do not compose into an end-to-end safety, watchdog, operation-step, or communication latency bound.
8. Production source contains a 512-byte local flash-save buffer and Arduino `String` construction in calibration, while no complete static RAM, heap, or stack budget is available.

## Unknowns and assumptions

- The unit and achieved hardware timeout corresponding to `IWatchdog.begin(10000000)` must not be assumed from this repository alone.
- CPU clock, interrupt priorities, Arduino core serial buffer sizes, Wire timeout behavior, CAN queue implementation, and HAL flash timing are not established by checked-in production code.
- No target logs or traces establish actual loop gap, `SystemYield()` duration, stop latency, peripheral transaction latency, CPU utilization, or queue occupancy.
- The ideal approximately 32 ms per-ToF cadence assumes continuous `get_Distance()` calls, no BMS quiet deferral, ready bus, and bounded successful I2C calls.
- Radio serialization estimates require assumptions about E22 framing, subpacket behavior, AUX semantics, on-air turnaround, interference, and external polling rate.
- BMS freshness is a software acceptance threshold, not proof that low-battery reaction within that age is safe.
- Finite parser and BMS frame buffers do not bound the number of junk bytes drained in one service call.
- Named CAN queue sizes do not prove the dependency's byte cost, ISR behavior, overflow behavior, or effective capacity on the selected core.
- The 512-byte flash-save local is not peak stack; nested calls, interrupt stacking, library internals, formatting, and compiler optimization are unknown.
- Arduino `String` is treated as likely heap use, but allocator behavior and exact allocations are outside the canonical production source.
- Operation timeout checks are assumed to use wrap-safe unsigned subtraction where shown; several older timing variables use signed `int`, so long-uptime behavior needs separate validation.
- The absence of a committed build/map/measurement artifact means no source-level estimate may be relabeled as a measured worst case.

## Validation obligations

1. Capture the exact toolchain, Arduino core, library revisions, CPU clock, interrupt configuration, and watchdog API semantics used on the production-equivalent target.
2. Produce link map, section sizes, per-function stack-usage files, static call-stack analysis, ISR stacking allowance, heap policy, and target stack/heap high-water measurements.
3. Instrument event-to-output latency for bumper, ToF stale, AS5600 stale, manual-link loss, command STOP, and watchdog starvation under combined worst credible CAN/UART/I2C/logging load.
4. Measure `SystemYield()`, each proposed V3 operation step, each peripheral adapter action, and scheduling jitter with percentile distributions and observed maxima tied to a reproducible workload.
5. Fault-inject stuck/slow I2C, continuous UART input, continuous CAN input, full TX buffers, radio AUX low, malformed BMS streams, and flash erase/program while observing safety and watchdog behavior.
6. Establish explicit byte/frame/time budgets and overload policies for safety/control, acquisition, and best-effort observability traffic.
7. Verify UART and CAN queue capacities, memory costs, ISR service behavior, overflow counters, and high-water marks on the selected core and libraries.
8. Replace or isolate execution-critical dynamic allocation and prove that post-initialization critical paths do not allocate.
9. Define per-sensor acquisition deadline, accepted observation age, stale-recognition deadline, and stale-to-safe-output deadline, then verify each separately.
10. Define bounded asynchronous contracts for motor, lifter, radio configuration, BMS, ToF, AS5600, flash, and logging before using their V1 local thresholds as V3 budget inputs.
11. Run an architecture proving slice for every execution candidate with identical synthetic load and fault cases, then record measured evidence without calling analytical bounds measured worst cases.

## Conclusion for architecture selection

V1 supplies many useful configured thresholds and local capacities, but it supplies no defensible end-to-end execution bound for the non-compensable gates.
The strongest architectural evidence is structural: safety, watchdog feeding, communication drains, sensing, telemetry, and operation progress share one cooperative call chain, and several members of that chain are unbounded by production source.
Therefore V1 cannot by itself justify a cooperative, RTOS, or hybrid winner.
Any candidate can pass only after it isolates the safety path, makes operation and adapter steps bounded, assigns single-writer peripheral ownership, provides bounded communication classes and overflow policy, and closes the listed target resource and timing obligations.
