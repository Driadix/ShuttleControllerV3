## 2. Protocol emulation vs реальный привод

### 2.1 Что говорит индустрия

Три класса практик HIL-стендов:

- **dSPACE-класс (full vehicle simulation)**: реальная ECU против real-time модели объекта (plant model) на SCALEXIO; модель замыкает все контуры кроме самой ECU. Используется именно потому, что повторяемость и контролируемость аварийных сценариев выше, чем с реальной физикой [S26], [S30].
- **OPAL-RT-класс**: real-time симуляция силовой электроники/приводов; подход «сначала замыкаем модель - потом переносим на железо», стенд трактуется как поверяемый измерительный прибор с известными границами [S23]. Практика явно говорит: timing-параметры (sample time, I/O scan rate, latency budget) фиксируются до расширения матрицы тестов, сигнальные пути проходятся от разъёма контроллера [S23], [S25].
- **NI-класс (signal-level / FIU)**: открытые PXI-платформы, fault-вставка через Failure Insertion Units - отдельные коммутационные модули, которые вводят обрывы/КЗ/дрейфы в сигнальные цепи [S24].

Общий знаменатель: **HIL проверяет реакцию ECU (контроллер, timing, обработку ошибок), а не физику объекта** - физически опасные/дорогие/неповторимые сценарии проверяются HIL, остаточная физика - на поле [S26], [S30].

### 2.2 Наш случай (VESC-FSESC75100, CAN 500k)

Факты о реальном приводе, критичные для решения:

- VESC-прошивка имеет **CAN timeout 0.5 с по умолчанию**: если контроллер VESC не получает кадры, мотор глушится. Для стабильной работы требуется постоянная посылка команд с фиксированной частотой (рекомендация 50 Гц) [S7]. Реальный VESC на стенде требует непрерывного потока SET_DUTY от тестируемого контроллера - скрывает класс дефектов «потеря команд», а сам становится источником собственных таймаут-стопов, разрушающих измерение T_fs.
- Статусные кадры (RX 2405 = CAN_PACKET_STATUS cmd 9, controller_id 101) конфигурируются в VESC Tool и передаются по расписанию [S7]; их содержимое на стенде должно быть контролируемым входом теста, а не свойством сторонней прошивки.
- Fault-injection против реального привода невозможен: flood/ошибки физического слоя/протокольные кадры на общей шине бьют по самому макету привода и могут вывести его из строя либо изменить его состояние непредсказуемым образом - нарушается детерминированность инъекции, которую ISO 26262-6 требует от fault-injection (точное время вставки определено до прогона) [S27].

**Рекомендация R1 (подтверждает решение карты #103)**: на стенде L5 работает **эмулятор протокола VESC-subset**, а не реальный привод. Состав эмулятора:

- Приём SET_DUTY (extended ID 100 на controller_id 100, ID 101 на controller_id 101, len 4, big-endian int32) - с регистрацией semantics в журнал прогона (что firmware реально «просит у привода»);
- Генерация CAN_PACKET_STATUS (2405 и 2404-класс по мере уточнения) с контролируемыми полями (ток, ERPM, напряжение) - это вход для порогов (ток лифтера 500 = интерпретации 100 мА/50 А до #104) и для HZ-16 по телеметрии;
- Приём и подтверждение force-stop кадра `0x00000001 / 0xFF x8` + регистрация точного времени приёма (орacle для F4: принял ли «привод» стоп-кадр);
- Flood/инъекторная функция в том же узле (см. раздел 5).

Граница: приводной реализм (инерция, D_brake, реальный ток, физика моторов) - полигон, как зафиксировано в решениях карты #103 (раунд 4). Это соответствует индустриальной схеме: HIL закрывает контракт и fault-поведение, поле закрывает физику.

## 3. Временная опора trigger→frame (C1 / T_fs ≤ 10 мс)

### 3.1 Сравнение источников времени

| Источник | Разрешение / точность | Известные ограничения | Источник |
| --- | --- | --- | --- |
| SLCAN (CANable stock fw) | Хостовые таймстампы, типично мс и хуже; известны баги со статичными/отрицательными таймстампами RX-кадров, путаница байтов extended ID с таймстампом; python-can: «better than nothing» | RX-путь через USB-CDC и планировщик ОС | [S1], [S2] |
| candleLight (gs_usb) | Аппаратные таймстампы 1 мкс, ставятся в RX-ISR контроллера устройства | TX-таймстамп - момент постановки в FIFO, не подтверждения на шине; чтение аппаратных таймстампов в ядре Linux только с 6.1 (candump -H); на Windows python-can/gs_usb - через pyusb+libusb (Zadig) | [S3], [S4], [S5] |
| Продакшн логический анализатор | До ~500 пс с 51-битным счётчиком (transitional timing) | Стоимость | [S6] |
| Любительский LA fx2lafw (Saleae-клоны, 24/48 МГц) | ±1 сэмпл асинхронной дискретизации (при 24 МГц = 42 нс) + таймдрейф ±50 ppm | Для T_fs = 10 мс ошибка < 1 мкс - несущественна | [S5], [S6] |

Вывод: для бюджета **10 мс** и даже для декомпозиции сублиллисекундных путей (T_isr, T_step, T_mailbox) разрешений любительского LA достаточно с запасом в 3 порядка; SLCAN-таймстампы - единственный класс, который для измерений T_fs непригоден вообще (джitter хоста сопоставим с самим бюджетом).

### 3.2 Рекомендуемая двухуровневая опора (R2)

Уровень 1 - **физическая опора (primary oracle)**: логический анализатор, подключённый к CAN_RX (и/или CAN_TX) и к дискретам (bumper-пины стендового стимулятора), частота >= 24 МГц; декодирование sigrok `can2` (поддерживает CAN 2.0, настройка битрейта, default 500 kbit/s, sample point 75%) [S6]. Правило sigrok: sample rate должен быть 4-5x от скорости самого быстрого события протокола; 24 МГц при 500 kbit/s даёт 48 сэмплов на бит [S6]. Двухуровневая синхронизация с firmware - по #52 §6.3: trigger-кадр по CAN + событийные метки с monotonicTick в envelope; LA-захват начинается по тому же trigger-кадру, так что обе шкалы (tick firmware и наносекунды LA) связаны одним событием.

Уровень 2 - **автоматизированные кампании**: candleLight (gs_usb) на Linux-хосте (`candump -H -t a`, ядро >= 6.1) как инъектор с аппаратными таймстампами; этот уровень даёт N прогонов без ручной обработки LA-захватов, а LA используется для золотых прогонов и калибровки расхождения часов (например, раз в кампанию).

Примечание для Windows-хоста: python-can `gs_usb` работает через pyusb+libusb (Zadig на устройство), но таймстампы на этом пути хостовые - для C1-измерений на Windows первичной опорой должен оставаться LA [S4].

Расходы на дешевизну: два узла (LA + candleLight) - нормальная практика: анализаторы фиксируют физический уровень (межкадровый интервал, ошибки, присутствие конкретного кадра), чего список SLCAN-кадров в принципе не видит [S5].

## 4. Оснастка power-cut

### 4.1 Индустриальные требования

ISO 26262-5: критерии верификации аппаратных элементов обязаны специфицировать operational environment, включая **supply voltage** и mission profile [S8]. Промышленные HIL автоматизируют питание ECU как штатный инструмент сценариев: программируемые БП симулируют профили батареи (cold cranking, dips, spikes) [S9]. Fault-injection по ISO 26262-6 применяется к компонентам и входам, включая цепи питания; вставка должна быть детерминированной по времени [S27].

### 4.2 Дешёвая реализация (R3)

**БП Riden RD6006 (или RD6006-W)**:

- Управление по **Modbus RTU через USB** (UART 115200 8N1 по умолчанию) или через Wi-Fi-модуль (TCP-мост на тот же Modbus RTU); регистровая карта документирована сообществом, есть готовый python-модуль (Baldanos/rd6006), SCPI в стоковой прошивке нет [S10], [S11].
- SCPI + Modbus TCP появляются при перепрошивке Wi-Fi-модуля альтернативной прошивкой Riden Dongle - рекомендуется, если кампании будет гонять verification-runner через единый lab-интерфейс [S11].

**Реле/ключ power-cut** (обязателен, БП один не справляется):

- Выходная ёмкость БП и конденсаторы платы растягивают спад напряжения: управлять «снятием питания» отключением выхода БП нельзя - фронт на входе платы определяется RC-постоянной, а не моментом команды. Need: последовательный ключ (N-MOS в разрыв минуса, ~100-900 А/десятки мОм, гейт с ускоренным драйвером, управление от оснастки/GPIO) или быстродействующее реле/твердотельное SSR в разрыв 12.5 V.
- Brown-out dips - снижением уставки напряжения БП (рампа 12.5 → низкий уровень → 12.5), что соответствует cold-cranking практике [S9]; сколь скоростная дип-рампа нужна - определить при уточнении бюджетов (#48), но точки снятия (save/staging/applying/mid-op/mid-GC) выбираются по событийным меткам фаз с monotonicTick (#52 §6.3).
- Доказательная часть: отвод на LA (2-й канал - напряжение питания через делитель/компаратор, или диф-пробник), чтобы фактический фронт питания попал в тот же захват, что CAN-кадры.

Коммутация power-cut и CAN-коммутатор физического слоя (раздел 5.2) образуют мини-FIU в терминологии NI/dSPACE [S24].

## 5. I2C stuck и CAN flood

### 5.1 I2C stuck-инъекция (R4)

Практика (kernel `i2c/gpio-fault-injection` docs, TI appnote, TotalPhase):

- Вставка дефекта «slave держит линию» = ключ к GND на SDA (или SCL), физически это то же, что зависший slave [S12], [S13].
- SCL stuck low - это бессрочный clock stretch; мастеру не помогает принудительно протактировать шину, восстановление возможно только reset/power cycle зависшего slave [S13], [S14]. Это меняет ожидания сценария: восстановление прошивки для SCL-stuck и SDA-stuck может быть разным (и должно быть разным по дизайн-обязательству №14 proving slice).
- Узаконенная процедура восстановления: перевести пины в GPIO, дать 8-16 тактов SCL (из них 9 - полный байт+ACK), дождаться отпускания SDA, затем STOP, пере-инициализация периферии [S12], [S13].

Перевод в наш стенд: I2C2 (PB10 SCL / PB11 SDA, 100 кГц, ToF 0x09-0x0C + AS5600 0x36). Коммутатор: две N-MOS (например, 2N7002/BSS138) на SDA и на SCL к GND, управление с оснастки (GPIO с быстрым фронтом); включение по фазе - в окно транзакции с конкретным адресом (условный «при BMS-транзакции» из #52 §6.2 означает составной сценарий, где параллельно идёт RS-485-обмен с BMS). Верификация восстановления - LA на обе линии: фактическое число клоков recovery и STOP до перехода в Degraded; это соответствует требованию проверять интенсивность восстановления осциллографом/анализатором войны [S13].

### 5.2 CAN flood (R5) - с поправкой на физику шины

Инструменты:

- **Протокольный flood**: candleLight + python-can (gs_usb) [S4]; плотный поток extended 8B-кадров с минимальным межкадровым интервалом. Индустриальная мера нагрузки: насыщение 100% (production-нормы ≤70%, для safety-critical ≤50%, поэтому 100% - уже за предельной) [S15].
- **Ошибко-генерация**: `canerrsim` (SocketCAN) генерит error-кадры программно [S16]; физические ошибки - снятие терминации 120 Ом (обозначено как практика), коммутация обрыв/КЗ реле [S15].
- Bus-off recovery контроллера наблюдается через счётчики ошибок (TEC/REC) и LA.

**Важная находка для карты**: на 500 kbit/s кадр extended ID, 8 байт занимает ~131 бит номинально (1 SOF + 32 арбитраж + 6 control + 64 data + 16 CRC + 2 ACK + 7 EOF + 3 IFS; stuff-биты добавляют до ~20 на худших data-паттернах) - т.е. ~262 мкс или **~3816 кадров/c максимум**, что на горизонте тика 10 мс составляет ~38 кадров. Критерий из #52 §6.2 «поток > 64 кадров/тик» физически недостижим на этой скорости. Рекомендация: в destination-пакете карты специфицировать сценарий как «инъектор пытается дать максимальную плотность (100% load) + приоритетные инъекции поверх», сохраняя проверяемые требования - drop + счётчик + событие + control-plane жив + T_fs не нарушен.

Физический слой: коммутатор на 2 реле (разрыв CAN_H/CAN_L, вставка/снятие 120 Ом терминации, КЗ пар) - дальнейшая детализация в #62 (оснастка CAN L4).

## 6. BMS-стимулятор (RS-485, протокол DdA5)

Протокол JBD (наш `BmsDdA5.hpp`): TX `DD A5 cmd 00 cksumH cksumL 77`, RX `DD cmd status len payload... cksum 77`; команды Basic 0x03 / Cell 0x04 / Device 0x05; поля: packVoltage_mV, ток, ёмкости, SOC (байт 19), NTC `i16BE-2731`, до 24 ячеек; 9600 8N1, полудуплекс с DE. Публичный протокол JBD подтверждает структуру (DD A5 request / DD 03, 04 ответ / DD 80 error, checksum - сумма с A5 по данные, two's complement) [S19].

**Рекомендация R6**: стимулятор = изолированный USB-RS485 адаптер (или второй F405 для честного полудуплексного DE-тайминга) + python-скрипт, который:

1. Отвечает корректными кадрами на 0x03/0x04/0x05 (валидный checksum!), сценарии значений параметризуются;
2. Генерят пункты сценариев: low-SOC (soc ≤ 20), NTC-перегрев (значение NTC), protectionFlags (OVP/UVP/SCP), FET-status, seriesCellCount - для HZ-10 и телеметрии HZ-16;
3. Имитирует staleness (молчание/задержанные ответы) и порчу кадров (битые checksum).
Молчание/битые ответы - дешевле и безопаснее, чем разрезание физической линии, и покрывает переходы fresh/stale по #52. Физическая линия A/B на XT23, терминация 120 Ом уже на плате (v1-sensor-io-facts).

## 7. Радио-аттенюация E22 (R7)

Семейство SX1262: TX до 22 дБм, чувствительность до -137 дБм (SF12/125k); LoRa link budget ~161 дБ (типовой расчёт с антеннами), т.е. запас между TX и чувствительностью больше 150 дБ [S20]. Наш E22: 27 дБм, канал 440.125 МГц, air 4800 бит/с - точный вариант модуля UNKNOWN до сайт-чеклиста, но порядок запасной энергии тот же: потеря линка «в комнате» естественно не произойдёт.

Практика: управляемую потерю пути в лаборатории имитируют аттенюаторы - пошаговым наращиванием затухания находят breakpoint линка и проверяют реакцию стека [S21], [S22]. Проводная (conducted) схема устраняет внешние помехи и не зависит от расстояния/ориентации антенн.

Перевод в наш стенд:

- Тракт между двумя E22 (или E22 стимулятора и E22 платы) через SMA-кабели, в разрыв - ступенчатый аттенюатор (набор пинов 1/2/4/8/10/20/30 дБ, суммарно >= 60-80 дБ) **мощностью >= 1 Вт** (27 дБм = 0.5 Вт);
- Проверяемые сценарии: потеря линка (линк-таймаут, backoff 5/30/120/600, probe), деградация до порога RSSI, а также защита измерительного приёмника от 27 дБм (Safe input часто ≤ 10 дБм - аттенюатор обязателен и для этой цели) [S22];
- AUX-hang не требует RF: удержание AUX (PC0) - GPIO-сценарий, покрывается стимулятором сигналов, не радиочастью.

## 8. Воспроизводимые сценарии и evidence (R8)

Индустриальная норма [S23]-[S26], [S29]:

1. **Сценарий = скрипт + параметры + пре/пост-условия + pass criteria с единицами и лимитами.** OPAL-RT явно требует определённые pass criteria с конкретными пределами по времени; timing-параметры (скорости интерфейсов, таймауты) фиксируются до прогона [S23].
2. **Автоматизация всего**: исполнение теста, питание ECU, шинная нагрузка, вставка отказов, отчёт - автоматизированы (у нас это role verification-runner; стыковка сценариев стенда с runner - отдельный гипертикет карты, «Not yet specified»).
3. **Workload metadata** обязателен к каждому измерению (активные прерывания, CAN-нагрузка, состояние движения, занятые очереди) - протокол уже разработан в #52 §6.3 и остаётся нашим нормативом.
4. **N прогонов**: стартовый минимум #52 - N >= 30 на сценарий с калибровкой по стабильности max; это согласуется с общими практиками серийных измерений (итеративный подбор N по ширине доверительного интервала) [S29]. У нас планировщик детерминированный, разброс задают нагрузочные паттерны, поэтому матрица workload-паттернов важнее простого роста N (#52 §6.3).
5. **Сохранение сырья**: к каждому прогону - LA-захват (.sal/.sr), CAN-лог с таймстампами, журнал firmware (bridge), конфиг стенда (прошивки инструментов, версии протокола эмулятора). Evidence-record оформляется по #52 §7.1; исторические ссылки защищены тегами `evidence/*` (#51/#53).
6. **Детерминированное время вставки неисправностей**: точка вставки определяется заранее и повторяемо - ISO 26262-6 требование к fault-injection [S27].

## 9. Открытые пункты для destination-пакета карты

- Переопределить CAN flood-критерий с «>64 кадров/тик» на достижимый «100% load + приоритетная инъекция» (раздел 5.2).
- Зафиксировать границу эмулятор/полигон по drive-реализму (R1) и контракт эмулятора с #104.
- Выбор реализации power-cut ключа и уточнение brown-out рамок с бюджетами #48.
- Stuck-SCL и stuck-SDA - разные процедуры восстановления firmware; сценарии специфицировать отдельно.
- Стыковка стендовых сценариев с verification-runner (форматы сценариев, evidence-контракты) - открыта в карте.

## 10. Ограничения

- Единицы тока VESC-статусов (интерпретация 100 мА) до подтверждения #104.
- Точный вариант E22-модуля (и его Ptx) - до сайт-чеклиста; направление рекомендаций не меняется.
- ISO 26262 использован как источник практик, не как сертификационная цель (решение карты).
